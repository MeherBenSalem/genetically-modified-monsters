# Porting Spore & Stem to another Minecraft version

The 1.21.1 workspace is the reference. A port is a copy of `1.21.1/` into a new workspace folder (for example
`1.21.4/`) plus the API changes of that version. The root `build.gradle` and `.github/workflows/publish.yml` each
need one line for the new workspace; `marketing/source/render.cjs` (`VERSIONS`) and the compatibility table in
`marketing/curseforge/description.md` list supported versions.

## What carries over unchanged

- **All generated resources** (`common/src/generated`): textures, sounds, language, recipes, loot tables, tags,
  worldgen and advancements are regenerated by `python3 tools/assets/build.py`. When a version renames a data
  folder or changes a JSON format, change the generator once and every resource follows.
- **Creature geometry and animations**: the rigs in `tools/assets/ss/entities/` are version-independent; only the
  Java emitted by `rig.py` / `anim.py` may need a different shape (see below).
- **Gameplay code** in `common/`, behind the `platform/` services. Loader code is limited to the registrars, the
  entry points and a few events (attributes, spawn placements, stripping, flower pots, client registration).

## Checklist by version line

Verify each item against the target version's mappings; this list is a starting point, not a substitute for
compiling.

### 1.21.2 – 1.21.4

- **Entity rendering uses render states.** `HierarchicalModel` and `EntityModel<Entity>` give way to
  `EntityModel<S extends EntityRenderState>`; renderers create and extract a state each frame, and models read it in
  `setupAnim(S)`. Move each creature's `AnimationState`s into its render state (`copyFrom` the entity's), keep
  `RigModel` as the base and adapt `GlowLayer` to the state-based `RenderLayer` signature.
- **Blocks and items need their id at construction** (`BlockBehaviour.Properties#setId`,
  `Item.Properties#setId`). The registrars already know the id: pass it into the factory.
- **Food and drink** become consumable components; `usingConvertsTo` moves to the use-remainder component.
- **Armor materials** are no longer a registry: they become data (equipment assets). `ModArmorMaterials` becomes
  a set of constants and the armor layer textures move to the equipment texture folders.
- **1.21.4:** item models get a client item definition per item under `assets/<ns>/items/`. Add it to the
  generator's item model writer.

### 1.21.5 and later

- Keyframe animations are baked against a model root before use; generate the `AnimationDefinition`s as before and
  bake them in each model's constructor.
- Tool and weapon items are configured through `Item.Properties` rather than `SwordItem` / `DiggerItem` subclasses
  (Foraging Knife, Bloomreaver).
- Spawn eggs no longer take colours in code; give each egg its own texture (the generator can draw them from the
  creature palettes).

### 26.x

- `ResourceLocation` is `Identifier`, and entity/block-entity save data goes through `ValueInput` / `ValueOutput`
  instead of `CompoundTag`. Both are mechanical renames across `common/`.
- Java 25 and Gradle 9 for the workspace (`java_version=25`), as in the previous 26.x roots.

## Verifying a port

1. `python3 tools/assets/build.py` then `./gradlew build` in the new workspace.
2. Start a dev server once, then `python3 tools/assets/check.py` (zero errors).
3. `./gradlew :fabric:runGametest` and `./gradlew :neoforge:runGameTestServer` (every test passes).
4. `tools/qa/smoke_server.sh fabric` and `tools/qa/smoke_server.sh neoforge` (fresh world, no errors).
5. Look at it in game with `tools/qa/devrun.sh` and `tools/qa/client.py`: every creature, every block, a huge
   fungus grove and the Myceliarch fight.
