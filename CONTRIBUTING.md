# Contributing

Thanks for contributing to Spore & Stem.

## Before you start

- Open an issue for substantial changes before a large implementation.
- Keep changes focused. Avoid unrelated refactors in the same pull request.
- Preserve compatibility-sensitive identifiers (`spore_and_stem` mod id, package names, registry ids) unless a
  change explicitly requires them.

## Development workflow

1. Fork the repository and create a branch from `main`.
2. Make the smallest coherent change that solves the problem. Content changes start in
   [docs/DESIGN.md](docs/DESIGN.md).
3. Resources are generated. After changing anything in `tools/assets/`, run `python3 tools/assets/build.py`
   (add `--no-sounds` to keep the audio) and commit the regenerated files under
   `1.21.1/common/src/generated/resources/` and `client/entity/geo|anim`. Start a dev server once, then
   `python3 tools/assets/check.py` must report zero errors.
4. Build the version root you changed from inside that folder (currently `1.21.1/`) and run
   `tools/qa/smoke_server.sh fabric` and `tools/qa/smoke_server.sh neoforge`.
5. Update documentation (`docs/USAGE.md`, the patch notes) when behaviour or release steps change.
6. Open a pull request with a clear summary and verification notes.

## Coding expectations

- Common code goes in `common/`; loader code only where a loader API is unavoidable, behind the services in
  `platform/`.
- Version folders are intentionally isolated. Do not share sources across versions with symlinks.
- Never hand-edit files under `src/generated/` or the generated `client/entity/geo|anim` classes.
- Textures are generated by code and must follow `tools/assets/STYLE.md`. Never copy vanilla or third-party pixels.
- Do not commit jars, logs, run directories, secrets or local IDE files.

## Reporting issues

- Use GitHub issues for bugs and feature requests.
- Include the Minecraft version, loader, mod version, reproduction steps and logs when possible.
